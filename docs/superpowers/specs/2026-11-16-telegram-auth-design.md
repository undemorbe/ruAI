# Вход по логину и паролю, подтверждение и 2FA через Telegram

Дата: 2026-11-16. Статус: дизайн согласован, ждёт плана реализации.

## Зачем

Вход по коду из письма не работает: Timeweb блокирует исходящие SMTP-порты VPS. Новый вход не зависит
от почты: логин и пароль, а защиту (подтверждение аккаунта, 2FA, восстановление пароля) даёт отдельный
Telegram-бот. Сервисом можно пользоваться и платить без Telegram, но тогда везде видна плашка
«Аккаунт не защищён».

## Решения

| Вопрос | Решение |
|---|---|
| Учётные данные | логин + пароль; email только в форме оплаты (чек по 54-ФЗ) |
| Бот | отдельный бот (не бот поддержки), обслуживает сам API |
| Транспорт бота | long polling `getUpdates` внутри процесса ruai-api; вебхука и маршрута в nginx нет |
| 2FA | сообщение в боте с кнопками «Подтвердить» / «Это не я» и 6-значным кодом для ручного ввода |
| Вход только через Telegram, без пароля | нет (Telegram остаётся вторым фактором) |
| Вход по коду из письма | удаляется целиком (база на проде пустая, переносить некого) |

## Аккаунт

- Логин: 3–32 символа `[a-z0-9_.-]`, начинается с буквы или цифры, хранится в нижнем регистре,
  уникален. Зарезервированные: `admin`, `support`, `root`, `ruai`, `chatgpt`, `system`.
- Пароль: 8–128 символов; не совпадает с логином. Хэш `scrypt` (`node:crypto`, N=2^15, r=8, p=1,
  соль 16 байт), формат `scrypt$N$r$p$salt$hash` (base64url). Сравнение `timingSafeEqual`.
- Регистрация: логин, пароль, повтор пароля, согласия (`RegisterConsent`, как сейчас, с записью в
  `consents`). После регистрации пользователь сразу вошёл.
- Вход без привязанного Telegram: логин + пароль → сессия (cookie как сейчас, 30 дней).
- Ответ на неверную пару всегда один: «Неверный логин или пароль». На несуществующий логин всё равно
  считается scrypt (по фиктивному хэшу), чтобы время ответа не выдавало логин.
- Регистрация с занятым логином: «Логин занят» (это не утечка: логин публичным не считается, но
  частота регистраций ограничена).
- Смена пароля в аккаунте: текущий + новый; сбрасывает все остальные сессии.
- Email: поле `email` в форме оплаты, обязательное; сохраняется в `payments.receipt_email` и в
  `users.email` (последний введённый, подставляется в следующий раз). Email не подтверждается и для
  входа не используется.

### Частота (в памяти, `Window`, как сейчас)

- Вход: 10 неудач на IP за 15 мин, 5 неудач на логин за 15 мин; превышение → 429 с `Retry-After`.
- Регистрация: 5 на IP в час, 200 на весь сервис в час.
- Неудачи пишутся в `auth.log` строкой `API_AUTH_FAIL ip=…` (фильтр fail2ban уже есть).

## Telegram

### Бот

- Создаётся в @BotFather. Токен в `/etc/ruai-api.env` как `TG_BOT_TOKEN` (вводит `api-setup.ts`
  скрыто, формат `^\d{6,12}:[\w-]{30,60}$`). Без токена API стартует, всё про Telegram отвечает
  503 `tg_off`, плашка не предлагает подключение.
- При старте `getMe` → имя бота для ссылок `t.me/<bot>`. `deleteWebhook`, затем цикл `getUpdates`
  (timeout 30 с, `allowed_updates: ["message","callback_query"]`); `offset` хранится в таблице `meta`,
  чтобы перезапуск не обрабатывал старые апдейты повторно.
- Принимаются только личные чаты (`chat.type = private`). Всё остальное игнорируется.
- Команды: `/start <token>` (привязка), `/start` без токена (что это за бот и ссылка на сайт),
  `/status` (к какому логину привязан). Прочие сообщения: короткая подсказка и ссылка на бота поддержки.
- Модуль `server/src/api/telegram/` с узким интерфейсом `TgApi` (`getMe`, `getUpdates`,
  `sendMessage`, `editMessageText`, `answerCallbackQuery`); в тестах подменяется заглушкой.

### Привязка (подтверждение аккаунта)

1. Сайт: `POST /api/tg/link` → `{ url, expiresAt }`. Токен 32 байта base64url, в БД только sha256,
   10 минут, у пользователя одна активная ссылка (новая заменяет старую).
2. Пользователь открывает `t.me/<bot>?start=<token>` и жмёт Start.
3. Бот: токен действителен и не использован, этот Telegram id не привязан к другому аккаунту →
   записывает `users.tg_id`, `tg_linked_at`, отвечает «Аккаунт <логин> подтверждён, вход теперь
   защищён». Иначе понятный отказ («ссылка устарела», «этот Telegram уже привязан к другому аккаунту»).
4. Сайт опрашивает `GET /api/auth/me` (раз в 3 с, пока открыто окно привязки) и видит `telegram: true`.

Один Telegram id ↔ один аккаунт (UNIQUE).

### 2FA при входе

1. Логин и пароль верны, `tg_id` есть → сессия не выдаётся. Создаётся заявка `login_challenges`:
   id (16 байт), user_id, хэш кода (HMAC pepper), ip, ua, 5 минут, 5 попыток, статус `pending`.
   Ответ `{ challenge: id, expiresAt }`.
2. Бот присылает: «Вход в ru-chatgpt.com: <браузер, ОС из UA> · <время МСК>. Код: 482 913»
   и кнопки [✅ Подтвердить] [⛔ Это не я]. `callback_data` = `ok:<id>` / `no:<id>`.
3. Кнопка принимается, только если `from.id` совпадает с `tg_id` владельца заявки, заявка `pending`
   и не истекла. «Подтвердить» → `approved`; «Это не я» → `denied`, бот советует сменить пароль.
   Сообщение редактируется в итог («Вход подтверждён» / «Вход отклонён»), кнопки убираются.
4. Сайт опрашивает `POST /api/auth/challenge` `{ id }` раз в 2 с: `pending` → ждём; `approved` →
   сессия (cookie), заявка закрыта; `denied`/истекла → ошибка, обратно к форме.
   Ручной ввод: `POST /api/auth/challenge` `{ id, code }`; неверный код −1 попытка, 0 попыток → заявка
   закрыта. Сессию выдаёт только этот запрос того же браузера (заявка привязана к случайному
   `challenge`-id, который знает только он), кнопка в боте лишь меняет статус.
5. Telegram недоступен (ошибка отправки) → заявка всё равно создаётся, сайт пишет «Не удалось
   отправить сообщение в Telegram, попробуйте ещё раз»; входа без второго фактора нет.

### Восстановление пароля

1. «Забыли пароль?» → логин → `POST /api/auth/reset`. Ответ всегда одинаковый («Если к аккаунту
   привязан Telegram, мы отправили туда ссылку»). Частота: 3 на логин в час, 10 на IP в час.
2. Если `tg_id` есть: бот присылает кнопку-ссылку `https://ru-chatgpt.com/reset#<token>` (токен
   32 байта, sha256 в БД, 15 минут, одноразовый). Токен во фрагменте, чтобы не попасть в логи nginx.
3. Страница `/reset`: новый пароль дважды → `POST /api/auth/reset/confirm` `{ token, password }` →
   пароль сменён, все сессии удалены, бот пишет «Пароль изменён». Пользователь входит заново
   (с 2FA).
4. Без Telegram восстановления нет: текст отправляет в бота поддержки.

### Отвязка Telegram

Кнопка в аккаунте → `POST /api/tg/unlink` → в бот приходит заявка «Отключить защиту?» [Отключить]
[Отмена] (те же правила, что у 2FA, 10 минут). Подтверждение → `tg_id` = NULL, остальные сессии
удаляются. Сайт показывает статус по `/auth/me`.

## Плашка «Аккаунт не защищён»

Показывается, пока `user.telegram === false` и Telegram на сервере включён:

- Чат: над полем ввода, компактная, с кнопкой «Подключить» и крестиком (скрыть на сутки,
  `localStorage`).
- Аккаунт: блок «Безопасность», не скрывается.
- Paywall и форма оплаты: строка под кнопкой оплаты, не скрывается.
- Страница успешной оплаты: «Подписка оплачена. Подключите Telegram, чтобы не потерять доступ».

Текст: «Аккаунт не защищён: без Telegram нельзя восстановить пароль и подтвердить вход».
Кнопка открывает окно привязки (QR и ссылка на бота, ожидание подтверждения).

Общий компонент `UnprotectedBanner.vue` с вариантами `compact | block | inline`.

## Данные

Миграция 3 (дописывается в конец, версия перечитывается внутри транзакции):

- `users` пересоздаётся (у SQLite нельзя снять NOT NULL): `login TEXT NOT NULL UNIQUE`,
  `password_hash TEXT NOT NULL`, `email TEXT` (без UNIQUE), `tg_id INTEGER UNIQUE`,
  `tg_linked_at INTEGER`, `admin_note`, `created_at`, `last_active_at`, `blocked_at`.
  Старые строки (только dev-базы): `login` = часть email до `@` + суффикс при совпадении,
  `password_hash` = недействительный (`!`), то есть войти можно только после сброса.
- `DROP TABLE auth_codes`.
- Новые: `tg_links (token_hash PK, user_id, expires_at)`,
  `login_challenges (id PK, user_id, code_hash, kind 'login'|'unlink', status, ip, ua, attempts,
  tg_message_id, created_at, expires_at)`, `password_resets (token_hash PK, user_id, expires_at, used_at)`.
- `payments.receipt_email TEXT`.
- `sweep` удаляет истёкшие записи этих таблиц.

## API

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| POST | `/api/auth/register` | `{ login, password, consent }` | `AuthView` + cookie |
| POST | `/api/auth/login` | `{ login, password }` | `AuthView` + cookie или `{ challenge, expiresAt }` |
| POST | `/api/auth/challenge` | `{ id, code? }` | `{ status: 'pending' }` или `AuthView` + cookie; 410 истекла/отклонена |
| POST | `/api/auth/password` | `{ current, password }` | 204 |
| POST | `/api/auth/reset` | `{ login }` | 204 всегда |
| POST | `/api/auth/reset/confirm` | `{ token, password }` | 204 |
| POST | `/api/tg/link` | - | `{ url, expiresAt }` |
| POST | `/api/tg/unlink` | - | `{ challenge, expiresAt }` |
| GET | `/api/auth/me` | - | + `login`, `telegram: boolean`, `tgEnabled: boolean` |

Удаляются `/api/auth/code` и `/api/auth/verify`. CSRF-проверка (`origin` + `x-requested-with`)
на всех POST, как сейчас. Схемы тел с `removeAdditional: false`. nginx: лимиты зоны `ruai_api_code`
переносятся на `/api/auth/login|register|reset`, `ruai_api_check` на `/api/auth/challenge`.

`User` во фронте: `email` остаётся (для формы оплаты), добавляются `login` и `telegram`.
`AuthService`: `register`, `login`, `challenge`, `changePassword`, `requestReset`, `confirmReset`,
`linkTelegram`, `unlinkTelegram`. Мок (`src/api/mocks`) повторяет правила и имитирует бота
(подтверждение через 2 с, код `000000`).

## Оплата

`/billing/checkout` только для вошедших (гость получает 401, сайт открывает регистрацию; так уже
сделано в форке). Тело получает `email` (обязательно, `isEmail`), он уходит в `payments.receipt_email`
и `users.email`. Создание пользователя по email из checkout удаляется.

## Админка

- Списки и карточка: логин вместо email; колонка «Telegram» (да / нет); email из оплаты в карточке.
- Поиск по логину и email. Фильтр «Без Telegram».
- Правка пользователя: email (для чеков) и заметка, как сейчас; логин не меняется.
- Действие «Сбросить пароль» не делаем (YAGNI): восстановление только через бота пользователя.
- Telegram id в интерфейсе и аудите не показывается; в аудите только id пользователя и действие.
- Демо-данные (`dataset.ts`): логины и доля пользователей с Telegram.

## Тексты и юридическое

- Политика ПДн: добавить Telegram id и логин в состав данных, цель «защита аккаунта»; email:
  «для чеков». Версия документов (`LEGAL_VERSION`) повышается.
- Страница входа: вкладки «Вход» / «Регистрация», ссылка «Забыли пароль?».
- Без длинных тире во всех новых текстах.

## Безопасность

- В БД: хэши паролей (scrypt), sha256 токенов, HMAC кодов. Ничего из этого не логируется.
- Сессия выдаётся только браузеру, который начал вход (знает `challenge`-id); бот лишь меняет статус.
- Callback принимается только от `tg_id` владельца; `callback_data` разбирается по белому списку
  `^(ok|no):[\w-]{22}$`.
- Токен бота: только в env (600), не попадает в логи (URL запросов к Telegram не логируются).
- После смены пароля, сброса и отвязки: остальные сессии удаляются.
- Заблокированный в админке пользователь не может войти, привязать или сбросить.

## Тесты

Сервер (`node --test`, заглушка `TgApi`, управляемые часы):

- регистрация: валидация логина и пароля, занятый логин, согласия, частота;
- вход: верный/неверный пароль, несуществующий логин, частота, fail2ban-строка, блокировка;
- привязка: токен, истечение, повторное использование, чужой Telegram, `/start` без токена;
- 2FA: подтверждение кнопкой, «Это не я», ручной код, неверный код до исчерпания, истечение,
  callback от чужого Telegram, сессию выдаёт только запрос с `challenge`-id;
- восстановление: одинаковый ответ, ссылка в бот, одноразовость, истечение, сброс сессий;
- отвязка с подтверждением; смена пароля; `offset` переживает перезапуск;
- миграция 3 на базе с данными версии 2;
- checkout: 401 для гостя, `receipt_email` сохраняется.

Фронт (Vitest): формы входа и регистрации (валидация), ожидание подтверждения (опрос, ручной код,
истечение), плашка (видимость по `telegram`, скрытие на сутки), окно привязки, мок-правила.

## Вне объёма

- Вход через Telegram без пароля, Telegram Login Widget.
- Подтверждение email, рассылки, восстановление через почту.
- Подключение OpenRouter и оплаты (отдельные шаги).
